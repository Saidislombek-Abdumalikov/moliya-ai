# Moliya AI V2 - Production Engineering Roadmap

## System Architecture Flow

```
                      +---------------------------------------+
                      |                 User                  |
                      +---------------------------------------+
                                          |
                   +----------------------+----------------------+
                   | (Opened in Telegram)                        | (Opened in Browser)
                   v                                             v
+-------------------------------------+       +-------------------------------------+
|         Telegram Bot / App          |       |         Standard Web Browser        |
+-------------------------------------+       +-------------------------------------+
                   |                                             |
                   | (Sends initData)                            | (Sends Firebase IdToken)
                   v                                             v
+-----------------------------------------------------------------------------------+
|                           Express Backend Server (Vite)                           |
|  - Validates initData via HMAC-SHA256 (Telegram)                                  |
|  - Validates Auth token via Firebase Admin (Fallback)                             |
|  - Translates verified Identity into a single Internal User ID                    |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
|                              Firestore Database ($0)                              |
|  - "users_mapping": maps Telegram/Firebase IDs -> unique Internal User ID        |
|  - "users/{internalUserId}": user profile, transactions, cards, and metadata     |
+-----------------------------------------------------------------------------------+
```

---

## Authentication Strategy & Identity Linking

1. **Telegram as Primary Identity**: When the application runs inside the Telegram Mini App, the frontend extracts the `window.Telegram.WebApp.initData` string.
2. **Backend Authentication Verification**: 
   - **Telegram Flow**: The frontend sends the raw `initData` to `/api/auth/telegram`. The backend computes the HMAC-SHA256 of the data using the `TELEGRAM_BOT_TOKEN` as the key secret, matching it against the signature hash to guarantee authenticity.
   - **Fallback Flow**: If accessed from a standard browser, the app falls back to Firebase Authentication, sending the Firebase ID Token to `/api/auth/fallback`.
3. **Internal User ID Mapping**:
   - The backend checks a highly secure Firestore collection (`users_mapping`) to see if the validated identifier (Telegram User ID or Firebase UID) is already linked to a unique internal `userId` (UUID).
   - If no mapping exists, the backend securely creates a new internal `userId`, establishes the mapping entry, and initializes a default user profile in Firestore.
   - The backend returns the unique internal `userId` and a short-lived custom session token/JWT.
   - The database stores all transaction collections, budget limits, cards, and AI histories strictly under `users/{internalUserId}`.

## Version 1.0 Engineering Roadmap

### Milestone 1: Backend Secure Auth Engine & User Linking Setup
- **Objective**: Implement server-side verification endpoints (`/api/auth/telegram`, `/api/auth/fallback`) and Firestore mapping layer for internal User ID lookup/generation.
- **Why it is necessary**: Moves authentication entirely server-side, securing API endpoints and isolating data records behind cryptographically verified identifiers.
- **Files that will be modified**: `server.ts`, `src/firebase.ts`, `firestore.rules`.
- **Risk level**: Medium (Core security foundation).
- **Dependencies**: Secure Firestore instance ($0 budget).
- **Testing checklist**:
  - [ ] POST `/api/auth/telegram` with valid `initData` returns verified status and internal `userId`.
  - [ ] POST `/api/auth/telegram` with tempered/invalid `initData` returns 401 Unauthorized.
  - [ ] POST `/api/auth/fallback` with valid Firebase ID Token returns internal `userId`.
  - [ ] Verify `users_mapping` collection successfully links external IDs to a single internal `userId`.
- **Rollback strategy**: Revert `server.ts` and Firestore rules modifications via Git checkout.
- **Estimated completion**: 1 day.

---

### Milestone 2: Frontend Auth Integration & State Sync (FinanceContext)
- **Objective**: Integrate Telegram WebApp SDK script, intercept application initialization, negotiate verification, and refactor `FinanceContext` to fetch/sync data exclusively under the verified internal User ID.
- **Why it is necessary**: Replaces localized/arbitrary client storage with highly secure, database-synced data linked to the authenticated user.
- **Files that will be modified**: `index.html`, `src/FinanceContext.tsx`, `src/App.tsx`.
- **Risk level**: High (Core state engine refactoring).
- **Dependencies**: Milestone 1.
- **Testing checklist**:
  - [ ] Launch app inside Telegram: handles loading/auth seamlessly, loads user data.
  - [ ] Launch app in external browser: redirects or initiates the Firebase fallback auth.
  - [ ] Add/update/delete transactions: updates are successfully written to `/users/{internalUserId}/transactions`.
- **Rollback strategy**: Revert frontend changes in `FinanceContext.tsx` and `App.tsx`.
- **Estimated completion**: 1-2 days.

---

### Milestone 3: Telegram Bot Integration & Webhook Handling
- **Objective**: Re-enable and secure Telegram Bot event handlers, set up production webhooks securely, and deliver high-performance automated greetings with Mini App entry buttons.
- **Why it is necessary**: Serves as the primary entry point and distribution mechanism for Telegram users.
- **Files that will be modified**: `server.ts`.
- **Risk level**: Low.
- **Dependencies**: Milestone 1, 2.
- **Testing checklist**:
  - [ ] Sending `/start` to the Telegram Bot returns an interactive reply button containing the correct Mini App URL.
  - [ ] Missing bot tokens in environment variables fail gracefully with a log message instead of crashing the server.
- **Rollback strategy**: Revert Telegram webhook additions in `server.ts`.
- **Estimated completion**: 1 day.

---

### Milestone 4: Private Admin Panel & Role-Based Authorization
- **Objective**: Secure the `/admin` route entirely behind backend role verification and Firestore-enforced security rules.
- **Why it is necessary**: Ensures public exposure of admin tools is impossible, maintaining absolute privacy of internal operations and metrics.
- **Files that will be modified**: `src/components/AdminScreen.tsx`, `src/App.tsx`, `server.ts`, `firestore.rules`.
- **Risk level**: Medium (Security critical).
- **Dependencies**: Milestone 1, 2.
- **Testing checklist**:
  - [ ] Attempting to navigate to `/admin` or query admin endpoints without administrative role metadata triggers immediate redirection or a 403 Forbidden error.
  - [ ] Authenticated administrator successfully logs in, views system metrics, and accesses configuration dials.
- **Rollback strategy**: Revert Admin route guards and rules changes.
- **Estimated completion**: 1 day.

---

### Milestone 5: Secure REST API Endpoints
- **Objective**: Apply robust authorization checks and token validations to other REST APIs (such as AI Parsing `/api/parse-expense`).
- **Why it is necessary**: Protects valuable AI processing resources (Gemini API calls) from denial-of-service attempts or unauthorized third-party consumption.
- **Files that will be modified**: `server.ts`.
- **Risk level**: Low-Medium.
- **Dependencies**: Milestone 1, 2.
- **Testing checklist**:
  - [ ] REST API endpoints refuse anonymous payloads with a 401 Unauthorized status.
  - [ ] Endpoints seamlessly parse authorized requests and compute replies within budget parameters.
- **Rollback strategy**: Strip API middleware authentication blocks.
- **Estimated completion**: 1 day.

---

### Milestone 6: n8n Workflow Integration
- **Objective**: Configure secure server-side webhook triggers to push completed transactions and financial alerts directly to an n8n endpoint for external workflows.
- **Why it is necessary**: Expands capabilities to trigger automated accounting workflows and sheets sync safely outside the core client thread.
- **Files that will be modified**: `server.ts`.
- **Risk level**: Low.
- **Dependencies**: Milestones 1, 2, 5.
- **Testing checklist**:
  - [ ] Adding a transaction sends an automated background webhook payload to the configured n8n URL.
  - [ ] n8n connection failures or timeouts are handled gracefully, ensuring zero latency or disruption to the user's interface experience.
- **Rollback strategy**: Disable webhook dispatch triggers in `server.ts`.
- **Estimated completion**: 1 day.
